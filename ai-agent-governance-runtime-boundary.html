AI agent governance at the runtime boundary

Governance must distinguish advisory evaluation from actual protected execution.

How it works

A proposal passes through trusted authority and state checks. The target integration owns protected credentials, executor and observed effect. Without a protected route, refusal is not evidence that every alternate execution path is blocked.

Where enforcement actually happens

A gateway can inspect a request, but the executor owns the effect. Identify every intended protected route and target credential, then establish the current authority source, pre-effect check and independent outcome observation. Any alternate route outside that coverage remains a deployment risk; reconciliation can detect only observed discrepancies.

Where should the control sit?

Separate proposal generation, authority ownership and protected effect. The agent may suggest an action; an authority provider determines business approval; a protected execution seam verifies the authorization and checks current state before effect. The executor—not the agent prompt—must own the protected credential. If a service bypasses this route, software verification at the intended seam does not prove that other route is blocked.

What if state changes after human approval?

Check the exact approved action and current authority at the point of commit. Expiry, revocation, changed amount, changed recipient or resource version can require a new decision. Do not interpret ALLOW as observed execution; require a separate outcome receipt or keep the outcome UNKNOWN. Inspect the controlled before/after proof.

Can human approval become stale?

Yes. Approval of one action does not automatically approve changed parameters or authority. In reviewed PR #201, the exact $250,000 path committed once with TRACE and the changed $260,000 path was refused with zero commits and no TRACE. Enforcement requires the protected route.
