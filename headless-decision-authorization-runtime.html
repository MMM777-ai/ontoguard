Deploy Decision Authorization inside the execution path.

OntoGuard Headless Decision Authorization Runtime 1.2.21 is the self-contained, pack-governed runtime for authorizing exact agent actions inside customer-controlled or confidential execution environments.

The Runtime is the embedded Decision Authorization and execution-binding surface. The Decision Authorization Platform is the organizational operating environment around the same authorization core.

Exact-action and fresh-state binding

Authorization applies to the exact proposed movement. A prior ALLOW does not survive material mutation. An ALLOW is not a reusable blanket permission for arbitrary later actions.

Formed authorization results carry cryptographically sealed authorization material binding the decision to the exact movement, decision basis, deployment pack, standing conditions and validity window.

Pre-transition standing

Before Decision Authorization forms, the Runtime can determine whether the proposed action has standing to enter authorization — standing, no standing, or not evaluable. If standing is absent or cannot be evaluated, the Runtime records nonformation rather than fabricating a BLOCK or ESCALATE decision.

Trusted governing context

Only trusted, authenticated governance material can establish the authorization context. Production pack selection is controlled by tenant configuration. The requesting agent cannot make its own governance pack, state, authority, evidence, or policy authoritative.

Bounded and full semantic provider profiles

Corridors can run a bounded semantic profile or a full decision-causal provider. The full profile can resolve ontology, retrieval grounding, longitudinal behavior, multi-epoch R7 semantic curvature, and evidence synthesis inside the execution environment. It does not call home to ontoguard.ai. Ontology and retrieval remain mechanisms supporting Decision Authorization — they are not the product category.

Fresh-state and pre-commit standing

Corridors can use one-time issue-and-consume authorization or opt into pre-commit revalidation. Where revalidation is required, current state, authority, evidence, and policy are obtained from trusted deployment adapters rather than caller assertions.

Authoritative revocation

An unconsumed authorization can be revoked by a trusted deployment authority. Revocation prevents future consumption. It does not rewrite history or claim to reverse a consequence that already formed.

Review-resolution binding

The Runtime can return ESCALATE and bind a subsequent reviewer resolution to the original authorization without rewriting that original decision. The Platform adds the Approval Desk, assignment, reviewer workflow, evidence management, and operating UI around that primitive.

Execution-evidence binding

The Runtime accepts independently signed execution receipts and verifies that the executed resource, state version, target, movement, and action binding match the authorization that was actually issued. Execution evidence does not retroactively change the decision; it establishes whether the authorized protected effect formed.

Consequence custody and behavioral history

Execution outcomes can be bound back to the authorization, retained as consequence evidence, and projected into durable behavioral episodes. Outcome and history delivery is decoupled from the core authorization response path.

Recovery Standing

Corridors can prevent a retry or related movement from acquiring fresh standing while the consequence of an earlier authorization remains unresolved. Independent outcome evidence can reconcile the effect as committed, not committed, or still unknown. Terminal resolutions remain immutable.

Trusted deployment boundary

Production authorization can operate inside an embedded execution boundary or with trusted context assembled by the confidential execution environment. The calling agent does not get to authorize itself by supplying the values that would decide the case.

Integration conformance

The Runtime includes bounded readiness and OEM integration-conformance checks so an integration can fail closed when required production trust sources are not actually connected.

Supervisor-middleware integration

The Runtime includes a bounded OpenShell-compatible adapter that can place Decision Authorization in a supervisor middleware path. Proposed HTTP/MCP activity is treated as observed candidate movement, while trusted state, authority, policy and evidence remain deployment-controlled. ALLOW can proceed; BLOCK, ESCALATE, nonformation and integration failure fail closed. This is an integration capability and does not imply an NVIDIA partnership or certification.

TRACE interoperability

Independently evidenced execution can be projected into systems such as AgenTrust TRACE. The integration is listed at the AgenTrust Verified tier. Verification covers published integration behavior against released packages; it is not hardware attestation, L5, or product certification.

Production deployment

The deployable unit is a signed runtime image paired with engagement-specific governance packs and trusted adapters. It has no operational dependency on ontoguard.ai or the main OntoGuard application. Source archives are not the production unit.

No OPAQUE partnership is claimed. Hardware attestation is not assumed by default. Production L5 and universal non-bypassability require deployment-route evidence.

OntoGuard Governance Pack v1.2.0 names the public artifact and schema line. OntoGuard Headless Decision Authorization Runtime 1.2.21 names the deployable runtime line. Those are separate version namespaces.
